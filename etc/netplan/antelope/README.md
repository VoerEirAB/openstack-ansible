Antelope host networking (antelope.voereir.io)
==============================================

Netplan files as running on the antelope nodes (captured October 2026). Unlike
the example in the parent directory, these are the real files; copy a host's
files to `/etc/netplan/` on that host and run `netplan apply`.

| Host      | OSA name  | br-mgmt              | SR-IOV PF (`enp8s0f1`) |
|-----------|-----------|----------------------|------------------------|
| voereir11 | infra1    | `01-netcfg.yaml`     | 16 VFs                 |
| voereir13 | compute1  | `01-netcfg.yaml`     | 16 VFs                 |
| voereir14 | compute2  | `01-netcfg.yaml`     | 16 VFs                 |
| voereir15 | compute3  | `50-cloud-init.yaml` | 16 VFs                 |

* `br-mgmt` (on `eno2`, MTU 9000) carries the management network
  172.16.227.0/24. On voereir11 it also holds the HAProxy VIPs
  172.16.227.126 (external) and 172.16.227.127 (internal).
* `virtual-function-count: 16` on `enp8s0f1` creates the SR-IOV VFs used by
  Neutron's `sriovnet1` (see `network_sriov_mappings` and
  `nova_pci_passthrough_whitelist` in `etc/openstack_deploy/user_variables.yml`).
  Without it the VFs are gone after a reboot and SR-IOV ports cannot be bound.
* `50-cloud-init.yaml` was generated by MAAS/cloud-init. If cloud-init
  regenerates it, the `virtual-function-count` line must be added again.
* The untagged `30.0.0.1xx` addresses on `enp8s0f1` do not answer (untagged
  traffic does not pass between hosts; VLAN 1000 tagged does). They overlap
  `sriov-net`'s subnet, so Neutron's allocation pool for `sriov-net` excludes
  them.
